PEDSIM SOCIAL-FORCE NAVIGATION (UP TO FIVE PEDESTRIANS)
====================================================
Deploy the optional patched dependency described in DEPLOYMENT.txt and
upstream-manifest.json first. The launcher checks all six patched source
hashes. The standard deterministic pedestrian launch is a separate source.

START
  bash /home/xcg/ws/src/cane_planner/plan_manage/scripts/start_pedsim_navigation.sh start --world blank --scenario crossing

The script sources both workspaces, generates the world and starts planner 3,
pedsim and the observation bridge (historical node name pedsim_single_bridge) on its own private master (default 11551).
It refuses an occupied port and never attaches to 11311. --port PORT selects
another unused port. --no-rviz runs without the RViz window for unattended tests.
The entry script currently contains a machine-specific primary workspace path;
adjust that path when deploying elsewhere.

MAPS AND SCENARIOS
--world blank (default): uses the four walls from upstream blank_world.xml,
translated by (-15,-15) into a centered 30x30m arena. The same wall centerlines
generate world.xml for pedsim and world.pcd for both the simulation cloud and
planner static map. Walls are represented in the PCD with 0.10m thickness and
heights 0.2..2.0m. A floor at z=-0.1m supplies known free coverage; obstacle
height filters exclude it. Sampling is deterministic and has no sensor noise.
The generation directory and metadata world.json are printed and retained.

--world office: retains the previous office2_modify.pcd projection and local
planner map configuration. scenarios.yaml describes the pedestrian route.

Both maps support headon, crossing and overtake. Blank also supports crowd_2
and crowd_5; use --scenario crowd_5 to start five interacting pedestrians.
blank_scenarios.yaml is the
source of truth for blank-world pedestrian start/goal/desired_max_speed and
suggested robot poses. Initial pedestrian speed is zero; the desired/max speed
drives SFM and caps velocity, while interactions can slow or deflect the person.

Suggested RViz setup for blank-world experiments:
  scenario    pedestrian start -> goal    robot start -> goal (heading +X)
  headon      (4,0) -> (-6,0)              (-5,0) -> (5,0)
  crossing    (0,-3) -> (0,6)              (-5,0) -> (5,0)
  overtake    (-2.5,0) -> (7,0)            (-5,0) -> (6,0)
The launcher only prints these robot poses; it sends no hidden start or goal.
Use RViz 2D Pose Estimate, then 2D Nav Goal. Relative timing remains operator
controlled. The existing deterministic PedestrianPanel remains separate. Blank
uses the new SocialPedestrianPanel, described below. Multi-person presets use
a pedestrians list with independent start, goal and desired_max_speed values.
The launcher passes the entire speed array to the patched simulator in XML
agent order. Initial velocity is zero. Office still uses YAML plus round restart.

INTERACTIVE BLANK SCENES
The blank launcher selects pedsim.rviz and enables the real simulator editor.
In the social-force panel, Add enters placement mode. Drag with Pedestrian Start
(P) to set a new/selected start and heading; Pedestrian Goal (K) sets its target.
Select with the list or Select Pedestrian (U), clicking within 1m of the person.
Configure desired speed 0..3m/s, stop / return once / repeat. Reference time only
computes goal = start + desired_speed * reference_time * heading; actual arrival
depends on social forces. Speed zero creates a stationary observed pedestrian.
Starts must be >=0.55m apart; endpoints need >=0.5m arena-wall clearance.

Apply, map endpoint edits, add/delete/clear, reset or load reset ALL pedestrians
to their configured starts and wait. Robot state and the input guard survive.
Start/Continue resumes people; Pause freezes them while the simulator continues
publishing fresh, physically stationary observations. Global pedsim pause is
not used: it would stop the paired heartbeat. New robot goals reset/start people
only when the corresponding panel checkbox is applied and enabled.

Save exports applied configuration, not unapplied fields or transient positions.
Load validates the whole YAML then replaces the scene. By default edits are
remembered per preset/context in ROS_HOME/cane_planner/social_editor/*.yaml
(ROS_HOME defaults to ~/.ros). Restart restores configuration, reset and waiting.
Empty scenes are remembered too. Corrupt memory falls back to the preset with
a warning. Write failures are shown in the panel. --fresh-scene neither reads
nor writes memory; --editor-state-file PATH chooses a separate cache file.
See docs/development/operator-visualization/social-scene-editor.md for the schema.

AUTOMATIC START AND STATUS
WAIT_GOAL: no navigation goal yet. WAIT_EDITOR_READY: scene not acknowledged yet.
WAIT_PLANT/WAIT_INPUT: waiting for fresh
post-goal LFPC /sim_odom and upstream PAUSED_READY. WAIT_PAIRED_OUTPUT: one
unpause call has been made; waiting for exact agent/used-robot-TF pairing.
RUNNING: fresh paired pedestrian observations are forwarded to the planner.
The robot's original-stamped /sim_odom supplies world->pedsim_user TF; pedsim
uses the actual LFPC position, including stationary heartbeat poses.
Within one round, after arrival send another goal, or re-place the robot using
2D Pose Estimate and then choose the next goal. The initialized LFPC plant keeps
publishing its true stationary pose while waiting, including after a pose reset;
no input is generated before an initial robot pose exists.

FAULT_RESTART_ROUND indicates latched stale/invalid input. Read
/pedsim_single_bridge/status and /pedsim_simulator/guard_status on this round's
master. Status messages publish on transitions. Input recovery and manual
unpause do not clear a true fault. The original 0.5s freshness limits remain.

RESET AND CLEANUP
Ctrl+C in the start terminal, wait for its owned processes to exit, then rerun
the same command and set initial pose/goal. This restarts the whole owned round.
The supervisor holds a per-port lock, verifies master PID and a random round
token, and cleans up only its own process groups. Do not remove lock files or
stop other ROS processes. Generated geometry files remain for inspection.

RECORD FROM ANOTHER TERMINAL
  bash /home/xcg/ws/src/cane_planner/plan_manage/scripts/start_pedsim_navigation.sh record --label pedsim_trial
For an alternate port, pass the same --port PORT to start and record. Recording
verifies the running round's identity; it never falls back to another master.
Ctrl+C in the recording terminal stops only that recorder.

VALIDATION AND REMAINING WORK
Current stage results and next steps are maintained in
docs/PEDSIM_IMPLEMENTATION_PROGRESS.md. The full main planner still accepts
zero through five pedestrians per frame (fresh empty remains valid). The planner receives positions/velocities,
not hidden pedsim goals or true forces; its current prediction remains CV.
